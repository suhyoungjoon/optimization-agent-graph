# optimization-agent-graph 기획

## 1. 목적

최적화 엔진을 "모델"로 보고, 그 모델을 **실행 → 결과분석 → 개선안 도출 → 검증(비교) → 개선적용**의 반복으로 계속 나아지게 하는 워크플로우 agent를 만든다.

코어 레포(`optimization-agent-harness`)는 "AI에게 맡길 수 있나"를 가리는 **비교 실험**과, 규칙 엔진 params를 개선하는 **개선 루프**를 구현했다. 이 레포는 그 개선 루프를 엔진과 무관한 **정식 워크플로우**로 만들고, 엔진을 규칙 엔진 → 솔버 → 학습형 모델로 바꿔 끼우며 계속 업그레이드하는 자리다.

원칙은 코어 레포와 같다. AI는 제안하고, 코드는 검증하고, 사람은 결정한다.

## 2. 핵심 개념

| 개념 | 정의 |
|---|---|
| 엔진 | `DomainPack.solve` 계약을 따르는 배정 로직. 규칙 엔진(M1), 솔버(M4), 학습형(M5) |
| 모델 | 엔진 + params 버전. 예: `rule@v3` |
| 챔피언 | 현재 운영 기준으로 지정된 모델 버전 |
| 도전자 | 개선안을 적용한 후보 모델 |
| 시나리오 세트 | seed·결함 조합의 묶음. 학습용(개선안을 만들 때 봄)과 검증용(판정에만 씀)을 분리 |
| 모델 레지스트리 | 버전별 params 스냅샷과 모델 카드(검증 결과, 승인 정보, 부모 버전)를 보관. 챔피언 지정과 되돌리기 제공 |
| 판정 기준 | 도전자가 챔피언을 대체해도 되는지 판단하는 규칙. 필수조건 위반 0건은 절대 기준, 나머지는 설정 파일에서 사람이 정함 |

## 3. 워크플로우

```
[1 실행] → [2 결과분석] → [3 개선안 도출] → [4 검증(비교)] → (승인 대기) → [5 개선적용]
   코드        AI+코드          AI+코드            코드                           사람+코드
```

| 단계 | 하는 일 | 입력 → 출력 | 코어 재사용 |
|---|---|---|---|
| 1. 실행 | 챔피언 모델을 학습용 시나리오 세트에 실행, validate·metrics | 챔피언, 시나리오 세트 → 결정 레코드, 지표 | `pack.solve`, `validate`, `metrics` |
| 2. 결과분석 | 실패 패턴과 원인 가설. 수치는 집계 도구 결과만 인용 | 결정 레코드 → 분석 리포트 | `analyze`, `Aggregator`, 근거 검사 |
| 3. 개선안 도출 | LLM이 params 변경안 제안, 코드가 허용 범위 검사 | 리포트, 챔피언 params → 개선안 목록 | `propose`, `params_errors` |
| 4. 검증(비교) | 도전자 대 챔피언을 **학습용과 검증용 세트 모두**에서 비교, 판정 기준 적용 | 개선안 → 비교표, 판정 결과 | `simulate_params`를 seed별로 반복 |
| 5. 개선적용 | 사람 승인 시 도전자를 새 버전으로 등록하고 챔피언 지정. 반려 시 기록만 | 승인 결정 → 새 모델 버전 | 레지스트리 (이 레포) |

**상태**: `running` → `analyzed` → `proposed` → `validated` → `awaiting_approval` → `applied` / `rejected`. 중간 실패는 `failed`(사유 기록).

**상한**: 개선 루프 반복 횟수, 단계별 LLM 호출 수, 검증 시간 예산은 `settings/workflow.yaml`에서 읽는다.

## 4. 코어와의 관계 (handoff.md 요약)

- 코어는 고정 ref로 설치한다. 최상위 이름 `core`, `domains`, `api`, `scripts`, `configs`와 겹치는 폴더를 만들지 않는다.
- 경로 기본값이 site-packages를 가리키므로 설정·DB·캐시·params 경로는 항상 인자로 넘긴다.
- dispatch 팩의 `validate`·`metrics`는 팩 생성 시 params를 쓰므로, 후보 평가는 `pack_factory(params)`로 팩을 새로 만든다.
- 개선안 상태 전이는 코어의 API 계층에 있으므로 이 레포에서 직접 구현한다.
- 코어의 공백 중 이 레포가 채우는 것: 여러 seed·검증용 세트 비교, 판정 기준의 코드화, 되돌리기.
- LLM 경로는 코어에서도 가짜 LLM으로만 검증되었다. 이 레포도 가짜 LLM 리허설로 흐름을 먼저 고정하고, 실제 API 실험은 별도로 한다.

## 5. 엔진 로드맵

| 엔진 | 개선 대상 | 비고 |
|---|---|---|
| 규칙 엔진 (M1~) | params (가중치, 매칭 범위 등) | 코어의 dispatch 규칙 엔진을 어댑터로 감쌈. 결정적, 0.1~0.4초 |
| 솔버 (M4) | 목적함수 가중치, 제약 완화 범위 | OR-Tools 등. 결정성(시간 제한, seed, 다중 최적해) 확보 필요. 결과는 validate로 독립 검증 |
| 학습형 (M5, 선택) | 파라미터 자동 탐색 → 배정 정책 | 과적합 확인을 위해 검증용 세트 필수 |

엔진을 바꿔도 워크플로우 코드는 바뀌지 않아야 한다. 이것이 이 레포가 증명할 핵심이다.

## 6. 마일스톤

| 마일스톤 | 내용 | 완료 기준 |
|---|---|---|
| M1 워크플로우 뼈대 | 코어 고정 설치·재사용 확인, 규칙 엔진 어댑터, 이 레포 소유 params 파일, 5단계 상태 머신, CLI, 승인 대기에서 정지, 실행 ID별 결과 저장, 가짜 LLM 리허설 | `workflow run --rehearsal`이 승인 대기까지 돌고, `approve`로 params 버전이 올라감 |
| M2 검증 강화 | 시나리오 세트(학습용·검증용), seed별 챔피언/도전자 비교 집계, 판정 기준 설정(`settings/workflow.yaml`), 모델 레지스트리(버전 스냅샷, 모델 카드, 챔피언 지정, 되돌리기) | 검증용 세트에서 효과가 사라지는 개선안을 판정이 걸러내고, `rollback`으로 이전 챔피언 복귀 |
| M3 UI | 워크플로우 화면: 5단계 가로 흐름, 단계별 결과 펼침, 단계 색 AI(주황)·코드(파랑)·사람(검정), 챔피언/도전자 비교표, 승인·반려, 모델 버전 이력 | 화면에서 실행 하나를 처음부터 승인까지 따라갈 수 있음 |
| M4 솔버 엔진 | 솔버 어댑터, 규칙 엔진과 같은 시나리오에서 비교, 솔버를 챔피언 엔진으로 워크플로우 실행 | 엔진 교체 시 워크플로우 코드 변경 없음 |
| M5 (선택) | 파라미터 자동 탐색(LLM이 범위 제안, 알고리즘이 탐색), 학습형 엔진 | 검증용 세트 기준 개선 확인 |

## 7. 결정이 필요한 사항 (M2 전까지)

- 판정 기준: 목표 지표(예: 할당성공률)와 허용 가능한 부작용 한도(예: 희망시간 일치율 하락 폭). 수치는 사람이 정한다.
- 시나리오 세트 구성: 학습용·검증용 seed 수와 결함 조합.
- UI 방식: 가벼운 웹(단일 페이지) 또는 다른 도구.

## 8. 향후 과제

- 레거시 데이터 로더 (필드 매핑 명세 → 시나리오 세트로 연결)
- 멀티에이전트 시뮬레이션 (고객·작업자·상담사 agent로 검증 환경 고도화)
- MCP 서버로 감싸 Claude에서 워크플로우 호출
